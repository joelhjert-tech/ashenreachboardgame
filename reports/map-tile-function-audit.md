# Map Tile Function Audit

> Phase 1 report-only audit. Generated from canonical runtime data at branch `ui/tv-movement-focus-mode`, commit `6bd4fc0`. No gameplay or content was changed before this report was created.

## Executive answer

Ashen Reach has **49 active map tiles**: 24 Outer, 16 Middle, 8 Inner, and 1 Center. Every tile has a stable ID, artwork reference, topology node, and registered board-text effect key, but the displayed and executable contracts are not consistently aligned.

| UNSUPPORTED | 0 |

The root cause is a split model:

- Printed threat icons and the single authored recurring tile challenge are executable arrival data.
- Board-space `textBox.effectKey` actions are executable, but are offered later as sector actions rather than represented in one arrival stack.
- `ruleText`, `textBox.text`, and tags are presentation fields. They are not parsed, and many reuse an effect authored for another tile.
- The server, phone, TV, and Map Inspector derive different partial views. No single projected record answers what is current, pending, optional, or complete.

## Canonical runtime path found

1. `MOVEMENT_RESOLVED` updates location and changes phase to `sector`.
2. `RoomServer.runAutomaticPhases` owns automatic arrival sequencing.
3. `startNextTileChallenge` starts recurring `onArrival` challenges in authored order.
4. `shouldDrawEncounterForCurrentSector` and `calculateExplorationDraws` fill printed red/blue/yellow lanes.
5. A resolved arrival encounter opens `action`.
6. The phone may submit `resolve-space-text` or enter an available service.
7. End turn rejects several pending records, but there is no one canonical eligibility result and blocked reason.

`resolveBoardSpaceEvent` is a read model only. Tile prose is never parsed into mechanics.

## Current canonical arrival order

```text
Movement accepted by server
→ location updated
→ recurring on-arrival tile challenges in authored order
→ printed Threat lanes filled and resolved
→ action phase
→ optional board-text action / shop / service
→ end turn
```

## Global audit findings

- **Threat draws:** executable from `threatIcons`; lane order is deterministic.
- **Fixed encounters:** none are directly authored on active board spaces.
- **Hazards/challenges:** only `rift-whispers-ashen-chapel` is a recurring typed tile challenge. Other hazard/anomaly tags are descriptive.
- **Multi-effect order:** challenge `authoredOrder` and threat-icon array order exist; board text/services sit outside that stack.
- **Shops/services:** inferred from tags and special server paths; tags are not authority.
- **Departure effects:** none are authored.
- **Repeat visits:** challenge progress resets on movement; other repeat policy is implicit.
- **Completion:** challenge and encounter state are tracked, but no complete arrival record is shared by all clients.
- **Reconnect:** pending challenges/encounters survive; a projected remaining-rule stack does not exist.
- **Single-player:** same resolver path, but multiplayer-only target rules need explicit no-target completion.
- **Rivalry:** private projections exist; tile metadata must not authorize private target disclosure.
- **Validation:** 0 missing effect keys, 0 unused keys, 0 choice mismatches. Semantic prose/effect agreement is not validated.

## Reachability and prompt status

All 49 tiles are present in the canonical graph; gated access remains server-authoritative. Registered board-text effects are phone-reachable in the action phase. TV shows the current encounter but not the full stack. Map Inspector shows raw rules/content/topology but lacks runtime support status, repeat policy, and detached arrival simulation.

## Audit gate conclusion

This is a semantic-authority and sequencing defect, not missing topology. Implementation may proceed by deriving functional markers from executable data, creating a stable server-owned arrival stack, repairing confirmed mismatches with typed behavior or honest lore-only copy, centralizing end-turn eligibility, and projecting the same stack to phone, TV, and Map Inspector.
